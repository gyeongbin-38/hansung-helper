# 보안·가용성 방어와 운영 확인

AI를 이용한 공격도 실제 진입 경로는 HTTP 요청, 로그인 시도, 외부 데이터와 모델 출력이다. 문자열 차단에만 의존하지 않고 인증·권한·데이터 범위와 자원 예산을 서버에서 제한한다. 이 문서의 값은 코드에 구현한 기본값이며, 운영 환경에 반영됐다는 뜻은 아니다.

## 구현한 자원 예산

| 경로 | 제한 | 초과·장애 처리 |
|---|---|---|
| JSON 본문 읽기 | 전체 15초, 기존 엔드포인트별 바이트 제한, isolate당 동시 읽기 32개 | 408/413/429. 청크마다 시간이 갱신되지 않으며 취소·종료 시 슬롯 정리 |
| 공개 스냅샷 캐시 | isolate당 12개·문자열 보수 추정 12MiB LRU, payload 추정 4MiB | 오래된 항목 제거. 초과 payload는 기존 자료/번들로 폴백 |
| 공개 스냅샷 DB 읽기 | 같은 kind의 동시 요청 병합, isolate당 다른 kind 4개, 실패 후 5초 재시도 완충 | 번들/보유 자료 유지. 이력 조회가 혼잡하면 404 대신 503 및 Retry-After |
| AI 상태 GET | 일일 상태 5초 캐시·동일 조회 병합 | 상태 페이지 연타가 매번 DB 읽기로 이어지지 않음. POST의 실제 한도 검증은 유지 |
| AI 실행 | D1 공유 동시 3개, 계정당 동시 1개, 실제 제공자 요청에 25초 AbortSignal, 참고 JSON 80KB | 혼잡은 429 및 30초 Retry-After. 본문·출력·역할 검사와 기존 10회/15분·100회/UTC일 제한 유지 |
| AI 장애 회로 | 30초 안의 transport/timeout 실패 3회 후 30초 대기, 이후 probe 1개 | 정책 위반·부적절한 답변·클라이언트 취소는 장애 횟수로 계산하지 않음 |
| 비인증 학교 로그인 | D1 공유 동시 3개, 같은 계정 동시 1개 | 대기열을 무제한 만들지 않고 429 및 10초 Retry-After. 혼잡 거절은 계정별 3회 자격 시도에 포함하지 않음 |
| 학교 연결 전체 | SchoolSession 생성부터 90초를 로그인·리다이렉트·조회·지연 수집이 공유. 개별 요청은 기존 15초 | 새 하위 요청으로 전체 예산이 갱신되지 않음. 기존 부분 수집·이전 결과 보존 흐름 유지 |

로그인과 AI의 슬롯은 새 테이블 없이 `academic_login_limits`의 `work:lease:*` 이름 공간을 사용한다. 단일 조건부 INSERT로 다른 Worker 인스턴스의 요청에도 제한을 적용한다. 로그인 슬롯 3개는 기존 인증 후 재수집 대기열 6개와 별도의 풀이다. 모든 학교 작업을 합쳐 3개라는 뜻은 아니다.

AI 슬롯은 60초, 로그인 슬롯은 120초 후 만료된다. 정상 완료 시 해제하며, 로그인은 응답 뒤의 수집 작업까지 슬롯을 유지한다. 해제에는 세대 값을 사용해 이전 작업의 늦은 완료가 새 슬롯을 삭제하지 못하게 한다. 클라이언트 취소는 제공자 promise가 100ms 안에 실제 종료되면 해제하고, timeout/종료가 불확실한 취소는 만료까지 보수적으로 유지한다. AbortSignal 전달만으로 원격 GPU 계산이 반드시 즉시 중단됐다고 보장하지 않는다.

`work:breaker:advisor`는 일반 만료 행 정리에서 제외한다. 만료 시각 이후에도 이 행이 있어야 복구 probe가 하나로 제한된다. 성공한 probe가 회로를 닫는다. 이 단일 행에 질문·응답·비밀번호·학교 쿠키는 보관하지 않는다.

## AI 공격에 대한 경계

- 모델에는 DB·학교 로그인·신청·삭제 도구를 연결하지 않는다. 모델이 만든 명령이나 JSON을 실행하지 않는다.
- 현재 세션의 허용 자료만 구성하고, 개인 요약은 동의할 때만 전달한다. 요청 전후의 세션 검증을 유지한다.
- 클라이언트의 과거 assistant 기록을 실제 모델 역할로 신뢰하지 않고 JSON 참고 자료로 구분한다.
- 명시적인 인증 정보 패턴은 전송 전에 거부한다. 모델의 외부 주소, 채팅에 인증 정보를 입력하라는 명확한 요구, 직접 작업을 완료했다는 일부 명확한 주장은 출력 단계에서도 거부한다. 일반 로그인 화면 사용법은 허용한다.
- 외부 공고·과목명·일정의 간접 주입, 인코딩·다국어 우회, 사실 왜곡 가능성은 남는다. 필터와 시스템 프롬프트를 완전한 인젝션 방어로 설명하지 않는다. 임의의 비밀값을 모두 알아낼 수 있는 탐지기도 아니다.

## 코드 밖에서 필요한 DDoS 방어

위 예산은 비싼 작업·메모리·제공자 비용을 보호하지만, 대규모 트래픽이 Worker에 도착하는 것 자체를 막지는 못한다. 여러 IP·데이터센터에서 오는 요청으로 Worker/D1 일일 한도를 소진시키는 공격까지 막으려면 엣지 설정이 필요하다.

1. 현재 `workers.dev` 접근 제어와 Cloudflare 요금제/한도·DDoS 설정을 확인한다. Cloudflare는 프로덕션에 소유한 zone의 Route/Custom Domain 사용을 권장한다. 소유 도메인이 준비되기 전에 기존 주소를 끄지 않는다.
2. 소유 zone에서 로그인·AI·재수집 POST 경로별 WAF/속도 제한을 설정한다. 일반 공개 GET·정적 파일과 같은 기준으로 묶지 않는다. 캠퍼스 공유 IP를 고려해 정상 피크를 관찰한 뒤 기준을 정한다. JSON API에 HTML challenge를 무조건 반환하면 정상 로그인도 깨질 수 있다.
3. Workers의 CPU/메모리 오류, 429/503 비율, D1 읽기·쓰기·대기, AI 사용량과 비용을 경보에 연결한다. 정상 요청 지연과 거절률을 같이 관찰해 기본 동시 처리 수를 조정한다. 비밀번호·학번·쿠키·질문 원문을 수집하지 않는다.
4. Workers Rate Limiting binding을 추가하더라도 데이터센터별 근사 제한이므로 엄격한 전역 동시 실행 슬롯을 대체하지 않는다. 현재 구현한 D1 슬롯은 유지한다.

이번 변경은 Cloudflare WAF·도메인·결제·경보 설정을 변경하지 않았다. 운영 트래픽에 부하 공격을 실행하지 않았다.

## 장애 대응

- AI만 불안정하면 기존 `HANSUNG_ENABLE_AI=0` 빌드/배포 경로로 추론을 끄고 기본 안내와 다른 학사 화면을 유지할 수 있다. 운영 배포는 소유자 절차를 따른다.
- 429는 의도적인 부하 완충일 수 있다. Retry-After를 무시하는 자동 재시도를 추가하지 않는다.
- AI 제공자가 복구되면 회로 대기 이후 probe 1개가 성공해 정상 처리 수로 돌아간다. 학교 자료는 수집 시각·부분 실패 표시를 확인하며 실계정 로그인 반복으로 상태를 점검하지 않는다.
- 기존 15분 주기 운영 모니터와 공개 데이터 점검을 유지한다. 키 교체나 운영 DB 삭제를 장애 복구 수단으로 사용하지 않는다.

## 검증과 한계

회귀 테스트는 메모리 SQLite/가짜 제공자로 여러 모듈 인스턴스의 동시 admission, 만료·늦은 해제, 회로 복구, 느린 본문, 취소, 캐시 상한·조회 병합과 정상 로그인/조회/상담 흐름을 검증한다. 실제 AI 모델에 대한 공격 성공률이나 운영 규모의 DDoS 저항성을 측정한 결과는 아니다. 운영 반영 후 실제 지연·오류·거절률을 확인해야 한다.
